### 2.1 영상 라벨 CSV (`영상데이터/교차로_14`) — 실제 차량, 통과 시점 기록

  - `departure_time`은 정확히 `photo 번호 × 0.5 s`다 **[확인]**. 즉 이미지는 **2 fps**이고 시각 해상도는 0.5 s다.
  - "정지선 통과"라는 의미는 열 이름(`departure`)과 회전 방향이 함께 적힌 점에서 유추했다 **[추측]**.
- **차량을 이어 궤적을 만들 수 없다** **[확인]**.
  - `Tracking_ID`가 5,069행 전부 0이다. 마스킹일 가능성이 있다 **[추측]**.
  - 위치·속도 열이 아예 없다.
- 신호 표시(`signal_info.movement`): `t`(직진) 2,796, `tl`(직진+좌회전) 1,606, `s` 606, **`y` 61** **[확인]**.
  - `s`에 통과한 차량은 우회전(203)과 유턴(317)이 대부분이다. 그래서 `s` = 적색으로 본다 **[추측]**.
  - `s`에 직진한 86건은 적색 위반 또는 라벨 오류로 보인다 **[추측]**.
  - `y` 직전 상태는 37개 황색 구간 모두 `t`였다 **[확인]**.
- **황색 시작 시각은 정확히 얻을 수 없다** **[확인]**. 신호 상태가 "통과한 차량이 있을 때"에만 기록되기 때문이다.

### 2.2 신호 데이터 (`신호데이터`, 부천시 12개 교차로, 2022-08-10)
- **CSV** 열: `interid, aringstarttime, signalstate, unix_time`. 상태가 바뀔 때만 한 줄이 기록된다(SinD와 같은 이벤트표) **[확인]**.
  - `signalstate`는 **SUMO 링크별 상태 문자열**이다.
    - 문자는 `G`(우선 녹색), `g`(비보호 녹색), **`y`(황색)**, `r`(적색) 4종이다 **[확인]**.
    - *i*번째 문자 = 도로망의 `<connection tl=… linkIndex=i>` 신호다. 12개 교차로 모두 net.xml에 있다 **[확인]**.
  - `unix_time` = `aringstarttime`(KST)을 epoch 초로 바꾼 값이다. 예: 08:00:22 KST → 1660086022 **[확인]**. **해상도는 1 s**다.
- **XML**(15분마다 SUMO `tlLogic`)의 phase 길이는 CSV와 정확히 맞는다. 예: 204820, 08:00 → G 22 s, y 4 s, G 84 s, … **[확인]**
- **CSV 시각의 의미에 함정이 있다** **[확인]**.
  - 행 시각을 해당 상태의 **시작**으로 읽으면 황색이 20–44 s, 녹색이 3–4 s가 되어 비현실적이다.
  - 행 시각을 해당 상태의 **끝**(= 다음 상태의 시작)으로 읽으면 다음과 같이 모두 맞는다.
    - 황색 길이: **3 s(14,461회) / 4 s(9,885회)**
    - 녹색 길이: 11–67 s
    - XML phase 길이와 일치
  - 따라서 정의상 해석은 "행 시각 = 그 상태의 끝"이다. 이때 **황색 시작 시각 = `y` 행 바로 앞 행의 시각**이다.
  - 이름이 `aringstarttime`(A링 시작 시각)인 것은 "다음 현시의 시작"이라는 뜻으로 보인다 **[추측]**.
- 결론: **신호 자체에서는 링크별 황색 시작 시각을 1 s 해상도로 얻을 수 있다** **[확인]**.

**시뮬레이션(SUMO) 출력이라고 보는 근거** — 각각은 정황이지만 모두 같은 방향을 가리킨다 **[추측, 근거는 확인]**
1. 가속도 분포가 **−4.5 ~ +2.6 m/s²에서 잘린다** (q0.001 = −4.50, q0.999 = 2.58). SUMO 승용차 기본값 `decel=4.5`, `accel=2.6`과 같다.
2. 정지한 차량의 차로 중심선 대비 **측방 오차가 q95 0.08 m**다. 차량이 기하학적 중심선 위에 있다는 뜻이고, GPS나 영상 추적으로는 나올 수 없는 값이다.

4. 위치 변화로 계산한 속도가 같은 시점의 `spd`와 일치한다(상관 0.999). SUMO의 오일러 적분 `x(t) = x(t−1) + v(t)·Δt`와 같은 패턴이다.
5. 폴더 이름이 "신호최적화데이터"이고 SUMO net/rou/edgeRelation이 함께 들어 있다 **[외부]**. 신호 최적화(강화학습 등) 시뮬레이션용 데이터셋으로 보인다.

### 2.4 정지선 위치 (`1200012n.net.xml`)
- SUMO netedit 1.14.1로 만든 도로망이다. 접합점 359개 중 신호 교차로 12개, `stopOffset`는 0개다 **[확인]**.
- SUMO에서는 **진입 차로 `shape`의 마지막 점 = 정지선**이다(SUMO 규약) **[외부]**.
  - 샘플에서도 정지한 차량이 차로 끝점에서 0 m(최소), 0.95 m(1%) 상류에 선다 **[확인]**. 대기열 선두가 차로 끝에 붙어 서는 것과 맞는다.
  - 그래서 **정지선은 net.xml에서 바로 얻을 수 있다.** 다만 이것은 *모델링된* 위치이고 현장에서 측량한 정지선이 아니다 **[추측]**.
- 영상 라벨(교차로_14)에는 지도·좌표가 없다. 정지선을 얻으려면 원본 영상에서 호모그래피를 직접 만들어야 한다.

## 3. 신호와 궤적 시각 맞추기 — SinD·NGSIM과 비교

| | SinD | NGSIM Peachtree | AI Hub 샘플 |
|---|---|---|---|
| 시계 | 신호 `timestamp(ms)` = 궤적 `timestamp_ms` (RawFrameID는 오답) | 신호 프레임 = 궤적 frame_id + k, k를 0~−1.5 s까지만 좁힘 | 둘 다 `unix_time` (초) |
| 해상도 | 0.1 s | 0.1 s | **신호 1 s / 궤적 1 s** |
| 검증 방법 | 적신호 통과율 | 적신호 통과율 | 같은 방법 (아래) |

검증 방법 (SinD·NGSIM과 같은 불변량):
- 차량이 처음 교차로 내부 차로에 들어간 시각을 진입 시각으로 본다(1 s 단위).
- 그 링크의 신호 문자를 보고 상태를 센다.
- 대상은 우회전을 제외한 진입 943건(12개 교차로)이다.

| CSV 시각 해석 | 진입 시 신호 비율 | 판단 |
|---|---|---|
| **행 시각 = 상태의 끝** (XML·황색 3–4 s와 일치) | 황 **75.4%**, 적 12.6%, 녹 12.0% | 물리적으로 불가능 |
| 행 시각 = 상태의 시작 | 녹 88.3%, 황 9.7%, 적 2.0% | 적신호 통과율은 그럴듯함. 그러나 이 해석에서는 녹색이 3–4 s, 황색이 20–44 s |

- 정의상 맞는 해석("끝")으로 보면, 진입의 **94%가 황색 시작 −2 ~ +5 s에 몰려 있다** **[확인]**. 녹색은 11–67 s(중앙값 39 s)인데도 그렇다.
- 실제 교통이라면 녹색 내내 진입이 퍼져 있어야 한다.
- 신호 대기 접근로의 행 중 **92.7%가 정지 상태(속도 < 0.1 m/s)**다 **[확인]**. 새벽 5시라 교통이 적은데도 대기열이 길다.
- 해석: **시뮬레이션이 신호 CSV를 "행 시각 = 시작"으로 잘못 읽어 돌린 것으로 보인다** **[추측]**. 그 결과 시뮬레이션 안에서 차량은 각 주기마다 3–4 s짜리 녹색과 20–44 s짜리 황색을 겪었다.
  - "시작" 해석에서 적신호 통과율이 2%로 낮은 것과, 진입 시각이 한 창에 몰리는 것 모두 이 가설로 설명된다.
  - 다른 가능성도 있다. 샘플이 시각을 마스킹했거나 이동시켰을 수 있다 **[추측]**.
- **어느 경우든 이 궤적에서 "황색에 사람이 서느냐 가느냐"를 배울 수 없다.**
  - 시뮬레이션 차량은 SUMO 차량 추종 모델의 규칙대로 움직인다.
  - 게다가 신호 길이 자체가 비현실적이다.
  - SinD·NGSIM에서는 시각 오차가 "몇 초"였다면, 여기서는 **신호 의미 자체가 어긋난다.**
- 전체 데이터에서 다시 확인할 것: 같은 검정에서 녹색 진입이 녹색 구간 전체에 퍼지는지, 그리고 위 두 해석 중 하나에서 적신호 통과율이 ≤ 5%가 되는지.

## 4. SinD 로더 형식(궤적 + 신호 + 정지선)으로 바꿀 수 있나

| 필요 요소 | 개별차량 CSV + 신호 + net | 영상 라벨 |
|---|---|---|
| 차량별 궤적 (x, y, v, 시각) | ○ 1 Hz (SinD·NGSIM은 10 Hz) | ✕ ID 없음, 위치 없음 |
| 신호 이벤트표 (링크별 G/y/r) | ○ 1 s, `y` 표기 | △ 통과 사건이 있을 때만 |
| 정지선 | ○ net.xml 차로 끝점 | ✕ |
| 접근로 ↔ 신호 매핑 | ○ `connection linkIndex`로 바로 연결 (SinD는 데이터로 추정해야 했음) | ✕ |
| stop/go 라벨 (`events.label_event`) | 형식상 가능 | ✕ 정지 차량 미기록 |
| **사람 운전자 행동** | **✕ 시뮬레이션으로 보임** | ○ |

- **기술적으로는** `ngsim.py`처럼 로더를 하나 쓰면 된다. 순서는 다음과 같다.
  - 위경도를 UTM으로 바꾸고 netOffset을 적용한다.
  - 진입 차로 끝점과 직전 점으로 SinD와 같은 `StopLine`을 만들고, `geometry.project`로 d를 계산한다.
  - linkIndex로 신호 상태를 붙인다.
  - `label_event`를 적용한다.
- 부족한 것은 다음과 같다.
  1. **실제 운전자 데이터가 아니다 [추측, 근거 다수].** "주변 사람 운전 차량"을 예측한다는 연구 질문과 맞지 않는다. 학습해도 SUMO 모델을 다시 배우는 셈이다.
  2. **1 Hz다.** τ = 0.5 s를 평가할 수 없다. 2 s 이력은 2개 점이라 LSTM 입력이 사실상 없다. 정지선 통과 시각 오차도 ±0.5 s다.
  3. **신호와 궤적의 시각 의미가 서로 맞지 않는다** (3절).
  4. 샘플은 새벽 5시 15분치뿐이다. `nxt_inter_sig_st` 등 신호 관련 열이 비어 있다. 전체 데이터에서 채워지는지는 미확인이다.
- **영상 라벨 + 이미지 경로**: 실제 차량이지만 다음 작업이 필요하다.
  - 원본 이미지에서 검출·추적을 다시 하고 호모그래피를 만들어야 한다.
  - 2 fps라 추적 품질과 속도 추정이 낮다.
  - 신호도 영상 속 신호등을 직접 읽거나 별도로 구해야 한다.
  - 샘플에서는 이미지와 라벨의 교차로가 달라 시도조차 할 수 없다.

## 5. 권고
- **본 실험 데이터로 쓰지 않는다.** SinD 전체 데이터(10 Hz, 실제 운전자, 정확한 신호 시계)가 계속 1순위다.
- 전체 데이터를 신청한다면 먼저 AI Hub 데이터 설명서에서 확인한다.
  - (a) 개별차량 데이터의 출처(실측/시뮬레이션)
  - (b) `aringstarttime`의 정의
  - (c) 영상 교차로 번호와 부천 `interid`의 대응
- 쓸 수 있는 부수 용도 **[추측]**:
  - 영상 라벨의 `y` 통과 기록으로 "황색 중 통과 차량 비율"을 교차로·시간대별로 집계한다. 학습 라벨이 아닌 기술통계 용도다.
  - SUMO 네트워크와 신호 프로그램으로 시뮬레이션 기반 사전학습이나 시나리오를 만든다.
